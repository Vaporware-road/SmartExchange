تصویر کلی

ما الان یک زیرساخت نسبتاً کامل در بک‌اند برای تمپلیت‌های تصویری داریم (Template + config JSON + render_template + preview)، اما در فرانت‌اند فقط یک Placeholder برای Template Editor داریم و رندررهای قدیمی (GBP/Tether/Special) هنوز مستقیم از مختصات هاردکد استفاده می‌کنند. هدف این پلن این است که:





همه‌ی بنرهای قیمت (GBP/Tether/Special) به‌مرور از روی Template JSON و Template Editor جدید در Vue رندر شوند.



Theme‌های مختلف هر بنر به‌صورت خودکار بر اساس نوع داده انتخاب شوند (مثلاً category vs tether vs special و نوع price).

برای اشاره به فایل‌ها، فرض می‌کنیم ساختار فعلی پروژه حفظ می‌شود:





بک‌اند: [backend/template_editor/models.py], [backend/template_editor/utils.py], [backend/template_editor/api_views.py], [backend/price_publisher/services/*.py].



فرانت‌اند: [frontend/src/views/templates/TemplateEditorView.vue], [frontend/src/views/templates/TemplatesDashboardView.vue], [frontend/src/services/api.js].

1) هم‌راست‌سازی مدل داده با نیاز جدید





استفاده از Template فعلی به‌عنوان هسته:





حفظ مدل Template با فیلدهای image و config در [backend/template_editor/models.py].



استفاده از همان config برای تعریف موقعیت و استایل متغیرها روی بنر.



تعریف اسکیمای توسعه‌یافته برای config:





در config، علاوه بر fields فعلی، یک لایه‌ی معنایی برای متغیرها اضافه شود:





variables: لیستی از متغیرها با کلیدهای معنایی مثل price_cash_buy, price_cash_sell, date_fa, date_en, time, pair_name, logo, channel_username.



هر variable شامل type (price/date/text/static), source_key (مثلاً مسیر داده در dynamic_data_dict) و تنظیمات پیش‌فرض.



فیلدهای تصویری (position/style) با variable_key لینک شوند تا بتوانیم چند Theme داشته باشیم بدون اینکه «معنای» متغیر گم شود.



تم‌ها (Themes) در config:





در config بخشی مثل themes اضافه شود که هر Theme را به‌صورت جدا تعریف کند:





هر Theme لیستی از layers داشته باشد؛ هر layer یک variable_key + x, y, font, size, color, align, max_width.



یک فیلد مثل default_theme_for_usage یا usage_typeها نگه داریم تا بعداً از روی نوع داده (Category/Tether/Special + نوع price) Theme مناسب انتخاب شود.



لینک Template به موجودیت‌های قیمت:





بررسی و در صورت نیاز، اضافه کردن/استفاده از FK مناسب بین Category / SpecialPriceType و Template (یا یک mapping مدل جدید) تا مشخص شود هر دسته قیمت از کدام Template و Theme استفاده می‌کند.

2) طراحی منطق انتخاب خودکار Theme در بک‌اند





تعریف usage types:





در بک‌اند (مثلاً در [backend/price_publisher/services/publisher.py] یا یک ماژول config)، چند نوع استفاده تعریف کنیم: category_board, tether_board, special_offer, و در صورت نیاز جزئی‌تر مثل special_buy vs special_sell.



نگاشت usage → theme_name:





در Template.config برای هر Template، یک دیکشنری usage_theme_map تعریف شود که می‌گوید برای هر usage_type از کدام theme استفاده کنیم.



گسترش render_template یا یک wrapper جدید:





یک تابع سطح بالاتر (مثلاً render_price_template(template, usage_type, dynamic_data)) اضافه کنیم که:





با توجه به usage_type, theme_name مناسب را انتخاب کند.



از config.themes[theme_name].layers برای رندر استفاده کند.



dynamic_data را از داده‌های دسته/تتر/اسپشیال پر کند (قیمت‌ها، تاریخ شمسی/میلادی، نام جفت ارز، لوگو، متن‌ها).



جایگزینی تدریجی رندررهای قدیمی:





در [backend/price_publisher/services/publisher.py] مسیرهای فعلی که به legacy_category_renderer, tether_renderer, special_offer_renderer می‌روند را طوری refactor کنیم که:





یک feature flag / تنظیم در SiteSettings مشخص کند برای هر نوع board از سیستم جدید استفاده شود یا قدیمی.



در حالت جدید، PricePublisherService به جای آن رندررها → Template + render_price_template را صدا بزند.

3) ساخت Template Editor در Vue (Drag & Drop)





API لایه Template Editor در فرانت‌اند:





در [frontend/src/services/api.js] یک سرویس جدید اضافه شود برای /api/template-editor/templates/:





متدها: list, retrieve(id), update(id, payload), updateConfig(id, config), preview(id, config?).



TemplatesDashboardView.vue در صورت نیاز طوری آپدیت شود که بتواند لیست Template‌ها یا حداقل لینک به Template Editor جدید نمایش دهد.



بازنویسی TemplateEditorView.vue:





این ویو باید:





Template مربوطه (image + config) را از API بگیرد.



بک‌گراند را به‌صورت یک canvas یا <div> با background-image نمایش دهد.



روی آن، layers مربوط به Theme انتخاب‌شده را به‌صورت باکس‌های draggable نشان دهد.



دکمه‌های بالا/پایین/چپ/راست برای nudge کردن مختصات هر لایه (۱px یا 5px).



پَنل تنظیمات برای لایه انتخاب‌شده:





متغیر متصل (variable_key از لیست variables)، فونت، سایز، رنگ، align، max_width.



سایدبار «کتابخانه متغیرها»:





لیست متغیرهای از پیش‌تعریف‌شده (prices, dates, branding) به‌صورت آیتم‌های drag source که روی Canvas Drop می‌شوند و یک layer جدید می‌سازند.



مدیریت Theme در UI:





در بالای Canvas یک selector برای Theme (مثلاً tabs یا dropdown) تا بین themeها سوییچ کنیم.



هر Theme layout خودش را دارد ولی متغیرها مشترک‌اند.



امکان Clone یک Theme از روی Theme دیگر برای ساخت سریع حالت‌های جدید.



همرسانی با Preview بک‌اند:





دو حالت:





Preview سریع در خود فرانت‌اند (تقریبی) برای جابه‌جایی سریع.



Preview واقعی: دکمه «Render with backend» که /preview/ را صدا بزند و یک تصویر واقعی از همان Template + config (با sample_data) نشان دهد.

4) تعریف کاتالوگ متغیرها (Prices / Dates / Branding)





کاتالوگ مرکزی متغیرها در بک‌اند:





یک ماژول (مثلاً [backend/template_editor/variables.py]) که لیست متغیرهای استاندارد را تعریف کند:





قیمت‌ها: price_cash_buy, price_cash_sell, price_account_buy, price_account_sell, tether_buy, tether_sell, و ...



تاریخ/زمان: date_fa, date_en, time با فرمت‌های متنوع.



برندینگ: logo, channel_username, website, phone.



هر متغیر شامل توضیح، نوع (string/number/image)، و تابعی برای استخراج مقدار از Category, SpecialPrice, SiteSettings و غیره.



استفاده در PricePublisherService:





هنگام ساخت dynamic_data برای render_price_template، از همین کاتالوگ استفاده شود تا نام‌گذاری و رفتار متغیرها یکدست بماند.



اکسپوز کردن کاتالوگ برای فرانت‌اند:





یک endpoint ساده در template_editor (مثلاً /api/template-editor/variables/) که لیست متغیرها را با متادیتا برگرداند تا فرانت‌اند همان را در Sidebar نشان دهد.

5) مهاجرت از رندررهای قدیمی به سیستم جدید





مرحله ۱ – پیاده‌سازی موازی (feature flag):





در SiteSettings یا یک config، امکان انتخاب «استفاده از Template Editor برای Category/Tether/Special» اضافه شود.



هر جا که الان legacy_category_renderer, tether_renderer, special_offer_renderer استفاده می‌شود، یک مسیر جدید اضافه شود که در صورت فعال بودن flag، از Template + render_price_template استفاده کند.



مرحله ۲ – ساخت Template معادل برای بنرهای فعلی:





با کمک Template Editor جدید، برای GBP و Tether و Special یک Template/Theme بسازیم که از نظر ظاهری نزدیک به بنر فعلی باشد.



تست خروجی‌ها در محیط تست/استیج و مقایسه با بنر قدیمی.



مرحله ۳ – سوییچ کامل:





بعد از اطمینان، flag را به حالت «استفاده از سیستم جدید» ببریم و رندررهای قدیمی را deprecate کنیم (در نهایت حذف، بعد از یک دوره).

7) نکات i18n و فونت





i18n:





تمام labelهای UI Template Editor در Vue از locales/fa.json و locales/en.json خوانده شوند.



برای متغیرهای تاریخ شمسی/میلادی، انتخاب فرمت در بک‌اند انجام و در توضیح متغیر برای کاربر توضیح داده شود.



فونت‌ها:





فونت‌های موجود در static/fonts با همان naming در UI نشان داده شوند (با preview کوچک در فرانت‌اند در صورت امکان).



در بک‌اند، همچنان از get_available_fonts() برای map نام UI → فایل واقعی استفاده شود.

۱) سیستم مختصات نسبی / Base Resolution

در بخش طراحی config و Template Editor:





در اسکیمای جدید config برای هر layer به‌جای ذخیره صرفاً x, y پیکسلی، یکی از این دو رویکرد را می‌گذاریم (قابل انتخاب در طراحی ولی در پیاده‌سازی فقط یکی را انجام می‌دهیم):





حالت درصدی: x_pct, y_pct در بازه \[0,1] که در بک‌اند به پیکسل واقعی تبدیل می‌شود.





یا حالت Base Resolution: نگه‌داشتن x, y روی رزولوشن پایه (مثلاً 1080x1080) و در رندر، نسبت actual_width / base_width و actual_height / base_height را اعمال می‌کنیم.





در TemplateEditorView.vue، کاربر روی Canvas با پیکسل کار می‌کند، ولی قبل از ذخیره، مختصات را به مدل انتخاب‌شده (درصد یا base_resolution) تبدیل می‌کنیم.





در render_price_template (یا wrapper render_template)، اولین مرحله قبل از رسم، Scale کردن مختصات بر اساس سایز واقعی template.image است.





۲) لایه‌ها با z_index (کنترل ترتیب رسم)

در اسکیمای config:





برای هر layer یک فیلد z_index اضافه می‌کنیم.





در رندر بک‌اند (Pillow)، قبل از Loop روی لایه‌ها، آن‌ها را بر اساس z_index (و اگر مساوی بود، بر اساس ترتیب تعریف) Sort می‌کنیم، بعد روی تصویر می‌کشیم.





در Template Editor UI:





امکان “Bring to Front / Send to Back” یا حداقل دکمه‌های Move Up / Move Down برای تغییر z_index لایه فعلی می‌گذاریم.





در لیست لایه‌ها (Sidebar)، ترتیب نمایش را هم از روی همین z_index می‌گیریم تا رفتار UI و رندر یکسان باشند.





۳) Preview دو مرحله‌ای (Fast vs Real)

در بخش Vue Template Editor:





Preview سریع (Front-end Only):





Canvas اصلی را با HTML/CSS (یا SVG) پیاده می‌کنیم: background-image + absolutely positioned div/span‌ها.





هر تغییر کوچک (درگ، Nudge، تغییر رنگ، سایز فونت) فقط DOM را آپدیت می‌کند؛ هیچ Request به سرور در این مرحله نمی‌فرستیم.





Preview واقعی (Backend / Pillow):





یک دکمه‌ی واضح مثل «Render Real Preview» می‌گذاریم.





با کلیک روی آن، config فعلی را (در صورت نیاز) برای /config/ می‌فرستیم و سپس /preview/ را صدا می‌زنیم و خروجی را در یک پنجره/تب Preview مجزا یا دیالوگ نشان می‌دهیم.





می‌توانیم برای UX بهتر، روی دکمه Preview یک محدودیت ساده بگذاریم (مثلاً اگر در ۲–۳ ثانیه اخیر Preview گرفته شده، دوباره نفرستیم) تا از اسپم‌شدن سرور جلوگیری شود.





روی دکمه‌ی «Save»، فقط config را ذخیره می‌کنیم؛ Preview گرفتن الزامی نیست، ولی معمولاً کاربر خودش قبل از نهایی‌کردن، Preview واقعی را می‌زند.
